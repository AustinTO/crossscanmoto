# OBDLink LX on iOS: compatibility options

## Finding

The public evidence does **not** establish a supported direct iOS connection from this app to an OBDLink LX. OBDLink documents the LX as a Bluetooth 3.0 product for Android and Windows, and its current programming manual classifies LX as **Classic Bluetooth**, separately from its BLE products. Apple's supported app paths for Bluetooth Classic accessories are ExternalAccessory for MFi accessories and CoreBluetooth's documented BLE/GATT APIs (including a transport-bridging option when a peripheral also has a BLE GATT connection). The public sources reviewed do not document a general iOS RFCOMM/SPP socket API for arbitrary Classic accessories.

This is a public-support finding, not proof that the LX hardware can never be made to work. The OBDLink MX+ is also Bluetooth 3.0, carries the same FCC ID, and OBDLink explicitly supports it on iOS. That means radio generation / FCC ID alone cannot explain the product difference. OBDLink has not published the LX's iOS accessory protocol, MFi status, or a third-party iOS SDK in the reviewed material. Vendor confirmation is needed before ruling out an undisclosed app-authorized ExternalAccessory path.

## Evidence

| Evidence | What it establishes | Limits |
| --- | --- | --- |
| [OBDLink LX product page](https://www.obdlink.com/products/obdlink-lx/) | OBDLink lists Android and Windows as the LX's supported platforms, specifies Class 2 Bluetooth v3.0, and lists FCC ID `X3ZBTMOD4`. | A support matrix alone does not prove a platform is technically impossible. The page does not name the Bluetooth profile or iOS API. |
| [OBDLink MX+ product page](https://www.obdlink.com/products/obdlink-mxp/) | OBDLink lists iOS, Android, and Windows; specifies Class 2 Bluetooth v3.0; and lists the same FCC ID `X3ZBTMOD4`. It explicitly describes LX as not iOS compatible. | Shared FCC ID means the certified radio module identifier is shared, not that firmware, MFi credentials, host configuration, or application protocol are identical. |
| [OBDLink Family Reference and Programming Manual, revision E](https://www.scantool.net/scantool/downloads/678/obdlink_frpm_e.pdf), §§3.1 and 8.12 | The manual's product table labels LX “OBD to Bluetooth,” MX+ “OBD to Bluetooth,” and CX “OBD to BLE.” Its footnote marks only selected products as supporting iOS. §8.12 explicitly lists LX and MX+ as Classic Bluetooth adapters, and CX/Carbyte as BLE adapters. `STBTI` / `STBTIX` report modem identity and distinguish Classic modem information from BLE modem information. | The manual does not identify the LX Bluetooth module as SPP or publish an iOS accessory protocol. Its modem-info commands can identify a unit's modem/revision, but do not expose MFi entitlements. |
| [FCC ID X3ZBTMOD4 filing record](https://fccid.io/X3ZBTMOD4) and its [2012 module manual entry](https://fccid.io/X3ZBTMOD4/User-Manual/Manual-1682393) | FCC record identifies Amp'ed RF Technology BTMOD4 as a Bluetooth module and links the original module manual titled `GeneralUserManual_BT33...`. | FCC radio authorization/frequency records do not establish SPP, BLE support, MFi status, the LX's firmware feature set, or the app-accessible profile. The FCC ID page is an archive mirror; it is not itself the FCC database. |
| [Apple External Accessory framework](https://developer.apple.com/documentation/externalaccessory), [Apple accessories guidance](https://developer.apple.com/accessories/), and [Apple QA1657](https://developer.apple.com/library/archive/qa/qa1657/_index.html) | ExternalAccessory is for MFi accessories over Classic Bluetooth; Apple says an accessory maker determines which apps may communicate and developers should obtain the accessory protocol specification. BLE accessories instead use CoreBluetooth. | These documents describe Apple's route; they do not say whether OBDLink LX has an MFi identity/protocol. |
| [Apple CoreBluetooth overview](https://developer.apple.com/documentation/corebluetooth) and [`CBConnectPeripheralOptionEnableTransportBridgingKey`](https://developer.apple.com/documentation/corebluetooth/cbconnectperipheraloptionenabletransportbridgingkey) | CoreBluetooth covers LE and BR/EDR-related scenarios. The transport-bridging option is specifically for connecting non-GATT Classic profiles when a BLE GATT connection to the same device exists. | The overview's mention of BR/EDR is not evidence of a generic raw RFCOMM/SPP API. Bridging does not provide an LE link to an LX documented only as Classic Bluetooth. |
| Local MotoScan 1.110 reverse-engineering evidence: [`transport-disassembly.txt`](transport-disassembly.txt) | Recovered Android code calls RFCOMM socket APIs, creates a socket by service UUID, and connects. This supports the Android Classic serial path used by the source app. | It is app implementation evidence, not an OBDLink statement that the product exposes a public iOS protocol or MFi access. |

## Options

| Option | Status | Requirements / implication |
| --- | --- | --- |
| **Use the current generic CoreBluetooth BLE transport with LX** | **Ruled out for the documented LX interface.** The vendor manual classifies LX as Classic Bluetooth and distinguishes it from its BLE adapters. | BLE scanning/GATT characteristic discovery cannot connect to a device that exposes no BLE GATT interface. Do not add guessed FFF0/NUS UUIDs for LX. |
| **Use iOS ExternalAccessory directly with LX** | **Unknown pending OBDLink confirmation; not publicly implementable from the material found.** | Need OBDLink to confirm that LX is MFi/ExternalAccessory-capable, authorize this app, and provide the protocol string / supported interface and any SDK or integration terms. Apple's framework requires this accessory-side contract. If the LX lacks the appropriate MFi/accessory implementation, an app-side Info.plist change cannot create it. |
| **Use CoreBluetooth transport bridging to reach SPP** | **Not supported by evidence for LX.** | Apple's bridge option requires a BLE GATT connection to the same device before requesting non-GATT Classic profiles. LX is documented as Classic rather than BLE, so it does not satisfy the documented prerequisite. |
| **Convert LX to BLE by firmware update** | **Unknown; no public evidence that this is possible.** | OBDLink says firmware updates are available, and the manual says some Bluetooth settings can be changed by firmware. Neither source claims LX can become BLE or gain a BLE GATT service. BLE requires LE-capable radio hardware as well as firmware; the FCC ID and the available module record do not settle whether the installed module silicon supports LE. Ask OBDLink for a model/revision-specific answer; do not treat a firmware update as a BLE conversion. |
| **Replace or redesign the radio / adapter hardware for BLE** | **Technically possible as a hardware project; not a firmware-only app change.** | Requires radio hardware that supports BLE, adapter firmware exposing a byte-stream GATT service, electrical/firmware integration, RF/regulatory work as applicable, and a documented UUID/characteristic contract. FCC's limited modular approval notes host integration conditions; see the filing. This would be a modified/new adapter, not an app-only fix for a stock LX. |
| **Build an external Classic-to-BLE bridge** | **Plausible engineering option; not validated with LX hardware here.** | A bridge device would connect to the LX over its supported Classic/RFCOMM path and expose a documented BLE GATT byte stream to iOS. It adds hardware, power, pairing, buffering, and protocol-forwarding work. The app's generic BLE transport can consume a discovered/configured GATT profile, but no bridge product/protocol is currently specified. |
| **Use an iOS-supported replacement adapter** | **Supported path if an adapter supplies a usable public interface.** | OBDLink advertises MX+ iOS support, and its manual marks MX+ iOS capable, but that does not imply the current app can use MX+ through a generic public API. For an app integration, choose a BLE/GATT adapter with a vendor-documented service/write/notify contract or obtain the OBDLink iOS SDK / accessory protocol. |
| **Use a relay device** | **Plausible workaround, not direct iPhone-to-LX.** | An Android device can run the Classic connection and relay data over a local network to iOS. This changes the topology and needs a relay service; it does not unlock RFCOMM on iOS. |

## What to ask OBDLink

Before committing to a direct LX iOS implementation, request written answers for the exact LX hardware and firmware revision:

1. Does the LX expose an Apple ExternalAccessory-compatible MFi protocol, and may this app register/use it?
2. Is there a public iOS SDK or protocol documentation for the LX (including the required ExternalAccessory protocol string and authorization steps)?
3. Does the BTMOD4 revision fitted to LX support Bluetooth LE in hardware, and is any vendor-supported firmware available that exposes BLE GATT? Ask for the service and characteristic UUIDs and the upgrade procedure.
4. Is the MX+ iOS route implemented through ExternalAccessory/MFi or another vendor API, and is that route intentionally absent from LX firmware/product configuration despite the shared FCC ID?
5. Can OBDLink offer a licensed iOS integration path for LX third-party apps, or recommend a supported alternative for direct iOS use?

## Bottom line for implementation

Keep the existing generic iOS BLE transport explicitly generic. Do not label the stock LX as iOS-compatible or present it as a BLE device. The viable direct path remains conditional on OBDLink supplying an authorized Classic accessory protocol/SDK or documenting an LX BLE capability that is not in the public sources reviewed. Otherwise, direct iPhone support requires a bridge or different adapter.
